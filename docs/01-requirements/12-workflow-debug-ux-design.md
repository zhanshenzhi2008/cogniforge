## 1. 要解决的问题（白话）

复杂流程里，一次调试会经过很多步，中间还可能多次「审批通过 / 拒绝」。  
用户需要分清两件事：

1. **这是哪一次试跑？**（今天上午点的那次，还是刚点的这次）
2. **这一次里面，审批属于哪一步？**（不是和别次混在一起）

当前「最近执行」只有扁平列表（状态 + 时间 + ID），**没有「试跑 → 步骤 → 人工操作」的层级**，所以会懵。

---

## 2. 信息架构（必须层级分明）

```
试跑（一次「开始调试」或「执行」）          ← 第 1 层
  ├─ 输入摘要（这次喂了什么）
  ├─ 整体状态（运行中 / 等待审批 / 完成 / 失败 / 取消）
  └─ 步骤时间线（本试跑内）              ← 第 2 层
        ├─ 节点 A  成功
        ├─ 节点 B（等待）  ← 你点了「通过」   ← 第 3 层：人工动作挂在步骤下
        ├─ 节点 C  成功
        └─ 结束     成功
```

### 规则

| 层级 | 含义 | 怎么产生 |
|------|------|----------|
| 试跑 | 点一次按钮 = 一条 execution | `POST execute` / `POST debug` |
| 步骤 | 该次里每个节点跑过的记录 | 已有 `node_runs` |
| 人工动作 | 审批通过/拒绝/继续/取消 | **现状**：只改 execution 状态，**没有独立动作日志**（缺口，见 §6） |

**点历史里另一条试跑时**：时间线、画布高亮、审批按钮全部切换到**那一次**，绝不串场。

## 3. 默认展示什么历史？

| 方案 | 结论 |
|------|------|
| 默认展开全部历史 | **否**。噪声大，看不出「当前在调哪次」 |
| 默认只看最近一次 | **是**。侧栏主区 = 当前/最近一次试跑 + 步骤时间线 |
| 更早的试跑 | 折叠成「更早的试跑 (N)」入口，点开再选；默认不铺满 |

保留历史的价值：对比两次输入、回看失败。但**不应和当前调试抢注意力**。

---

## 4. 从某个节点开始调试

| 项 | 说明 |
|----|------|
| 现状 | **没有**。每次都从开始节点整图跑（或 resume 从挂起处继续） |
| 需求 | 复杂图调试时，希望「从这个节点往后试」，跳过前面已验证的步骤 |
| 依赖 | checkpoint / 注入上游变量 / 可选跳过已成功节点 |
| 优先级 | **P1 backlog**（产品需要，但依赖引擎能力，不假装已有） |
| 入口设想 | 节点右键或配置抽屉：「从此调试」 |

## 5. 每个节点要不要固定展示「核心信息」？

### 画布上（始终可见）

| 固定展示 | 是否必要 | 说明 |
|----------|----------|------|
| 类型图标 | **必要** | 远看区分 LLM / Agent / 检索 / 等待 |
| 节点名称 | **必要** | 业务语义 |
| 边框色（按类型） | 建议保留 | 辅助扫视 |
| 运行态高亮 | **必要（调试时）** | 跑到哪、失败哪 |

### 画布上（不要默认全挂）

完整配置（模型 ID、Top-K、超时秒数、提示词全文等）**不要**堆在节点卡片上，否则图不可读。  
点开抽屉再编辑。

### 调试时可选增强（建议后续）

选中节点或时间线点到某步时，侧栏展示该步**摘要**：状态、耗时、错误一句、输出截断。  
仍不是把配置表贴在节点上。

## 6. 已知缺口 / 半成品

| 项 | 状态 | 说明 |
|----|------|------|
| 试跑层级时间线 | 首批补 Web | 用 `node_runs` 展示本试跑步骤 |
| 人工动作审计日志 | **缺** | 通过/拒绝没有独立事件表；只能从 waiting→running/failed 推断 |
| 默认折叠更早历史 | 首批补 Web | 见 §3 |
| 从节点开始调试 | **首版已做** | `start_from_node`；见 §4；上游输出灌入待后续 |
| 条件分支真/假边绑定 | **已加强** | 上下口常显「真/假」；连线着色+标签；抽屉出口说明；引擎按句柄独占 |
| loop / http / code / delay 配置面板 | **缺或极弱** | 后端有 config，前端抽屉几乎只有名称 |
| search 已补面板 | 可用 | KB + query + Top-K |
| 卡住的 running 历史 | **已加强** | 更早试跑可取消活跃项；>10 分钟标「可能卡住」 |

## 7. 结束节点：图标与是否必要

| 问题 | 结论 |
|------|------|
| 要不要「结束」节点？ | **要**。引擎与拓扑需要明确终点；没有 end 时「跑完」语义不清，也不好挂最终输出 |
| 图标是否 OK？ | 原「旗子」偏弱。改为 **对勾圆**（完成）更直观；开始用播放、结束用完成，成对记忆 |
| 能否只靠最后一个业务节点当结束？ | 不推荐。编排规范、一键成图、调试高亮都依赖显式 end |
